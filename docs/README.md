# docs/ — the phone app

A static progressive web app: the same spaced-repetition study loop as `apps/quiz_runner.py`, plus all 123 readings, running in Safari on an iPhone and installable to the home screen. Progress syncs through Supabase, so the phone and the laptop share **one** queue and **one** history.

This folder is both the source and the deploy root — GitHub Pages serves it directly, which is why it's named `docs/` rather than something tidier. There is no build toolchain: no npm, no bundler, no framework. The only generated files are under `content/`, produced by `apps/build_web.py`.

```
docs/
├── index.html              app shell — top bar, view container, bottom tab bar
├── style.css               mobile-first, light + dark, safe-area aware
├── app.js                  views, routing, the study loop
├── sm2.js                  SM-2 — a tested port of apps/scheduler.py
├── session.js              which items a session serves (pure)
├── analytics.js            stats + calibration maths (pure)
├── store.js                content loading, localStorage, offline write queue, sync
├── supabase.js             auth + the four REST calls, hand-rolled over fetch
├── config.js               ← YOUR Supabase URL + anon key go here
├── sw.js                   service worker (offline)
├── manifest.webmanifest    home-screen install
├── .nojekyll               stops GitHub Pages running Jekyll over this
├── icons/                  generated by apps/make_icons.py
└── content/                generated by apps/build_web.py — do not hand-edit
    ├── items.json          712 items
    ├── readings.json       123 readings, pre-rendered to HTML
    └── version.json        content hash, for cache busting
```

## Setup

### 1. Build the content bundle

```bash
python apps/build_items.py     # items/*.md  -> items/build/items.json
python apps/build_web.py       # wiki/ + research/ + items -> docs/content/
python apps/make_icons.py      # only needed once
```

`build_web.py` renders the markdown to HTML ahead of time, resolves every `[[wikilink]]` to an in-app route, wires the `[S3]` citations to their source notes, and computes backlinks. It reports broken wikilinks and any item whose `source_page` didn't make it into the bundle — both are `lint` findings, not fatal.

### 2. Create the Supabase project

Nothing here needs a CLI.

1. [supabase.com](https://supabase.com) → **New project**. Any region near you; note the database password Supabase asks you to set (you won't need it again for this).
2. **SQL Editor → New query** → paste all of [`supabase/schema.sql`](../supabase/schema.sql) → **Run**. That creates the two tables, the row-level-security policies, and the `record_attempt` function. It's idempotent, so re-running later is safe.
3. **Authentication → Users → Add user** → *Create new user*. Use your email and any password. Tick "Auto Confirm User" so you skip the confirmation email.
4. **Project Settings → API**. Copy the **Project URL** and the **anon public** key.

### 3. Point the app at it

Edit [`config.js`](config.js):

```js
export const SUPABASE_URL = 'https://abcdefgh.supabase.co';
export const SUPABASE_ANON_KEY = 'eyJhbGciOi...';
```

Both are safe to commit and safe to serve publicly. The anon key is a *public* client key; the RLS policies in `schema.sql` are the actual security boundary — a request can only ever touch rows whose `user_id` matches the signed-in user.

### 4. Point the laptop at it

Create `.env` at the repo root (gitignored):

```
SUPABASE_URL=https://abcdefgh.supabase.co
SUPABASE_ANON_KEY=eyJhbGciOi...
SUPABASE_EMAIL=you@example.com
SUPABASE_PASSWORD=the-password-from-step-2.3
```

Then check it and seed the history you already have:

```bash
python apps/sync_supabase.py status     # what's local, what's remote, what differs
python apps/sync_supabase.py push       # 712 state rows + 554 attempts -> Supabase
```

`push` is idempotent — attempts are deduplicated on `(user_id, item_id, ts)` — so re-running it is harmless.

> **Do not** put the `service_role` key anywhere. Not in `.env`, not in `config.js`. It bypasses RLS entirely and nothing here needs it: the Python scripts sign in as the ordinary user, exactly as the phone does.

### 5. Deploy to GitHub Pages

1. Commit and push, `docs/content/` included — Pages serves what's in the repo.
2. Repo **Settings → Pages** → Source: **Deploy from a branch** → Branch: **master**, folder: **/docs** → **Save**.
3. A minute later it's at `https://<you>.github.io/psych-undergrad/`.

Every later `git push` redeploys. Two things to know:

- **The repo is private, but a Pages site is public.** The readings and items become world-readable at that URL. Your *progress* stays private — that's in Supabase behind RLS. Pages for a private repo also needs GitHub Pro; without it, make the repo public or deploy to Vercel/Cloudflare Pages instead (both take the same `docs/` folder through their web UI, no CLI).
- Pages has no SPA rewrites, so the app uses hash routing (`#/read/concept-empathy`) and every path in it is relative. `apps/test_web_logic.py` fails the build if an absolute path sneaks in.

### 6. Install on the iPhone

Open the URL in **Safari** (not Chrome — only Safari can install a PWA on iOS) → Share → **Add to Home Screen**. It then launches full-screen with no browser chrome, and works with no signal.

## Using it

**Study** — the loop from the desktop runner, unchanged in substance: predict your confidence *before* seeing anything, answer, reveal alongside the source reading, grade yourself, scheduler updates. Cloze and MCQ auto-grade but you can always override. Mode, length, and unit/Bloom/type focus are all on the setup screen.

The confidence step is five buttons rather than the desktop slider — a slider is a poor target on a phone, and the values (10/30/50/70/90) sit mid-band for the calibration buckets. Committing to a number is the point; precision isn't.

**Read** — all 123 pages, grouped by unit, with working wikilinks, backlinks, full-text search, and tappable `[S3]` citations that show the source note. Any page with items on it offers **Quiz me on this**.

**Stats** — due forecast, streak, accuracy by Bloom level, weakest clusters, and the calibration chart: bar = how often you were actually right, line = how sure you felt. Distance between them is the fluency illusion, made visible.

**You** — sign in, sync status, content version, home-screen hint.

At the laptop, `1`–`5` sets confidence, `Enter` reveals, `1`/`2`/`3` grades.

## How syncing works

Supabase is the source of truth *across devices*, never a prerequisite for studying.

- Grading writes to localStorage immediately and puts the attempt on a durable queue. The queue drains when there's a network. Lose signal mid-session and nothing is lost; the sync chip shows `3 queued`.
- `apps/quiz_runner.py` calls `scheduler.sync_down()` once at launch and pushes each grade as you make it. Offline, those grades go to `.supabase-outbox.jsonl` and are sent on the next launch (or by `sync_supabase.py flush`).
- `review_state.json` and `review_log.csv` keep being written as a git-tracked local snapshot and offline fallback. `sync_supabase.py pull` refreshes them from Supabase.
- Conflicts resolve last-write-wins per item, except that an item with an unsent attempt is never overwritten by a pull. Two devices can only actually disagree if both studied the same item while offline.

With `config.js` left blank the app runs local-only: progress lives in that browser and the You tab says so.

## After changing content

```bash
python apps/build_items.py && python apps/build_web.py
git add -A && git commit -m "..." && git push
```

Then on the phone: **You → Check for new content**. That clears the service-worker caches and reloads, because a plain refresh would be served the old bundle.

## Tests

```bash
python apps/test_sm2_parity.py    # docs/sm2.js vs apps/scheduler.py
python apps/test_web_logic.py     # parse, session, analytics, assets, views + the loop
```

There's no node on this machine, so both run the JavaScript under JavaScriptCore via `osascript -l JavaScript`.

The parity test is the one that matters most. The phone and the laptop write to the same `review_state` rows, so if the two SM-2 implementations disagree by even a day, an item's schedule silently depends on which device you graded it on and nothing would ever surface the drift. It replays ~45k transitions through both and diffs them. (The trap it caught: Python's `round()` breaks ties to even, JavaScript's `Math.round()` breaks them upward, and a 'shaky' grade computes `round(interval / 2)` — so a 5-day interval becomes 2 days in Python and would have become 3 in a naive port. 500 of the reachable values differ.)

`test_web_logic.py` renders every view and drives three real grades through the loop, checking the scheduler advanced, the log was written, and the answer never appears during the prompt stage.

### Verifying on the phone

What tests can't reach is layout and touch. Worth a look the first time:

- [ ] Bottom tabs sit above the home indicator; the top bar clears the notch
- [ ] Tapping a text answer doesn't zoom the page (that's the 17px input rule)
- [ ] A wide table in a reading scrolls inside itself; the page never scrolls sideways
- [ ] A `[S3]` citation opens the source sheet
- [ ] Dark mode looks right — set iOS Appearance to Dark
- [ ] Airplane mode: the app still opens, a session still runs, the chip shows `offline`, and the attempts upload when the signal returns
- [ ] Grade something on the phone, then launch the Streamlit runner — the sidebar should report the pulled change
